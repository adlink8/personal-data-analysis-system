# Wiki 重新设计方案（用户反馈记录）

> 本文记录用户对 v1.5 Wiki 的重新设计思路，与当前 `docs/wiki/` 的开发文档无关。
> 对应预规划：`.planning/future-milestones/v1.5-personal-knowledge-wiki-projection/`

## 当前 v1.5 设计的问题

原设计（确定性投影）：Wiki 从三个结构化权威（personal_state / decision / external）读取已提炼好的断言，直接组装成 JSON 信封返回。

用户反馈：

1. **三个结构化权威覆盖范围太小** — personal_state / decision / external 只是全量数据中极小的一部分，大量原始数据（对话、KU、事件、记忆）未被纳入
2. **确定性组装可读性差** — 返回的是 `{"claims": {"current": [...]}}` 机器格式，不是人能直接读的话
3. **分层不对** — 不应只读三个已提炼好的子集，而应基于全量数据生成

## 重新设计方案

### 定位

Wiki 是**检索层内部的一个 LLM 驱动的可读摘要缓存层**，按主题/方面划分，直接接入检索层。

### 数据来源

Wiki 的数据来自检索层覆盖的**全部底层数据**，不限于现有三个结构化管道：

| 数据源 | 状态 |
|--------|------|
| Agent 对话 | ✅ 有 |
| GPT 对话 | ✅ 有 |
| Google 活动 | ✅ 有 |
| 知识单元 KU | ✅ 有 |
| 长期记忆 | ⚠️ 存量，管道已停 |
| 事件（personal_events） | ⚠️ 存量，管道已停 |
| personal_state 断言 | 范围太小 |
| decision 决策 | 范围太小 |
| external 外部事实 | 范围太小 |

### 按方面切分，不是按数据源切

每个方面跨所有数据源拉取相关数据：

```
检索层（跨源拉数据，不限 20）
    │
    ├─ [项目方面] ← Agent 对话 + GPT 对话 + Google + KU + 记忆 + 事件
    ├─ [技能方面] ← 同上，全源
    ├─ [教育方面]
    ├─ [职业方面]
    ├─ [健康方面]
    ├─ [财务方面]
    └─ [兴趣方面]
```

### 生成流程（后台任务）

```
1. 检索层拉全源数据（Wiki 专用批量通道，不限 top_k=20）
2. 按方面切分
3. 逐方面 LLM 提炼摘要
4. 汇总所有方面摘要 → LLM 生成 Wiki 可读页面
5. 写入 Wiki 层（检索层内）
```

### 用户请求路径

```
用户搜索
    ├─ Wiki 命中 → 直接返回 Wiki 页面
    └─ Wiki 未命中 → 正常走现有检索返回，不做额外操作
```

### 约束

1. **Wiki 接入检索层** — Wiki 页面是检索层的一部分，后续检索可以召回 Wiki 内容
2. **Wiki 本身就是缓存** — 不需要另外再套缓存
3. **不限 20** — Wiki 拉数据走专用批量通道，不走 `search_knowledge_units` 的对话级上限
4. **不回写 Chroma/KU** — Wiki 内容存在自己那层，不污染原始检索索引
5. **Wiki 生成是后台工作** — 不在用户请求路径上同步执行

### 与现有管道的差异

| 维度 | 原 v1.5（确定性投影） | 重新设计 |
|------|----------------------|----------|
| 数据来源 | 仅 personal_state / decision / external 三个已提炼权威 | 检索层全源数据（对话/KU/事件/记忆/…） |
| 生成方式 | 纯代码组装 JSON | 分片 LLM 提炼 → 汇总 LLM 生成 |
| 输出 | 结构化 JSON 信封 | 可读自然语言页面 |
| 是否写入检索层 | 否（只读投影） | 是（Wiki 是检索层的一部分） |
| 缓存策略 | 每次重新组装 | 自身就是缓存层，数据不变不重跑 |
