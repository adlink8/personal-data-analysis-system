## 二、已修正项详情（含证据）

### 1. `README.md` — 双 Wiki 混淆风险

- **问题：** 仓库同时存在"开发/运维 Wiki"（本目录）和候选中的"Personal Knowledge Wiki Projection"（v1.5），两者名字相近、职责完全不同。
- **证据：** `.planning/future-milestones/v1.5-personal-knowledge-wiki-projection/SPEC.md` 第 31-38 行明确列出两种 Wiki 及其状态（v1.5 为 `candidate_not_activated`，代码中无 `wiki`/`topic_page`/`backlink` 路由）。
- **修正：** 在 `README.md` 顶部加入澄清提示，说明两者关系及 v1.5 当前未激活。

### 2. `02-directory-structure.md` — 源码树遗漏三个顶层目录

- **问题：** `src/personal_knowledge/` 源码树列出了 `core/retrieval/services/application/intelligence/governance/evaluation/cli.py`，但遗漏了实际存在的 `domains/`、`adapters/`、`external_context/`。
- **证据：** `ls src/personal_knowledge/` 显示这三个目录确实存在；`domains/knowledge/build_canonical_knowledge_units.py`（9 行）内容为 re-export facade：
  ```python
  """Re-export facade — retained for backward compatibility during the 2026-08-13 cleanup window.
  Canonical location: application/knowledge/build_canonical_knowledge_units.py"""
  ```
  `governance/policies/architecture.yaml` 顶部注释也确认："Phase 21 domains slimming ... domains/ retains rules/models/constants + re-export facades until 2026-08-13"。
- **修正：** 补充三个目录到源码树，并注明 `domains/` 是遗留 re-export shim（计划 2026-08-13 后清理）。

- **问题 2：** "分层依赖规则"一节把依赖关系简化为"core 只能引用自己 / retrieval-application-services 引用 core+同级 / governance 独立"，与实际 7 层依赖图不符（例如 `services` 实际可以引用 `application`，`application` 可以引用 `retrieval`+`evaluation`+`domains`，并非"同级")。
- **证据：** `governance/policies/architecture.yaml` 第 18-33 行 `modules:` 段落逐层定义 `may_import`：
  ```
  core: layer foundation, may_import: [core]
  vector(retrieval): layer infrastructure, may_import: [core, knowledge, conversation, vector]
  conversation/knowledge/...(domains): layer domain, may_import: [core, source_adapters, ...]
  pipeline(application): layer application, may_import: [core, source_adapters, conversation, knowledge, memory, graph, vector, evaluation, pipeline]
  evaluation: layer evaluation, may_import: [core, conversation, knowledge, vector, evaluation]
  services: layer delivery, may_import: [core, conversation, knowledge, memory, graph, vector, pipeline, services]
  governance: layer control, may_import: [governance]
  ```
  与 `README.md`（仓库根）"Source layers" 表一致。
- **修正：** 按 7 层实际顺序重写依赖规则说明，并提示"真要判断合法性直接查 architecture.yaml"。

### 3. `03-tool-layer.md` — Decision Cockpit UI 接口表严重不完整

- **问题：** 页面"REST API 快速导航 → Decision Cockpit UI"只列了 `/ui/overview`、`/ui/system/status`、`/app/` 三条，实际已实现 11 条 `/ui/*` 路由（还有 `personal-state`、`external/delta`、`decision-queue`、`decision/workspace`、`actions/recent`、`proactive/summary`、`calibration/overview`、`evidence/resolve`）。
- **证据：** `src/personal_knowledge/services/api_server.py` 第 24-36 行接口列表注释逐条列出全部路由；第 604-613 行路由分发表确认实现存在。
- **修正：** 补全全部 `/ui/*` 路由到表格，并加入提示："Decision Cockpit（v1.4，Phase 36–40）截至本次审计仍是进行中里程碑（`.planning/ROADMAP.md` 标 🚧）……不代表产品已宣称完成"，同时注明该表可能滞后于新增接口，以 `api_server.py` 头部注释为准。

### 4. `06-merge-compression.md` — 遗漏一道关卡 + 示例数学错误

- **问题 A：** L1 真重复检测描述为"三重校验"（余弦→原始 Jaccard→区分度），遗漏了代码中实际存在的第三道关卡"语义骨架 Jaccard ≥ 0.75"（`L1_SEM_JAC`）。`10-faq.md` 中"阶段 A：构建合并层"一节其实已经正确列出了四阶段（含 0.75 骨架 Jaccard），06 页与之不一致。
- **证据：** `src/personal_knowledge/application/graph/build_merge_layer.py`：
  ```python
  L1_SEM_JAC = 0.75   # L1 语义骨架 Jaccard 门槛(去数字/路径后,防结构相似假阳性)
  ...
  if best_raw < L1_JAC or best_sem < L1_SEM_JAC:
      all_pass = False
  ```
  （第 83、260 行）
- **问题 B：** 原示例"两条骨架相同 → 唯一值=1 → 1/2 = 0.5 < 0.5 → 通过 ✅"存在自相矛盾：`0.5 < 0.5` 为假，按代码 `if ratio >= L1_DISTINCT_RATIO: all_pass = False`（第 267 行），ratio=0.5 时该样本组实际会被判定为**不通过**（降级到 L2），而不是原文声称的"通过"。
- **修正：** 在流程图中补上 `L1_SEM_JAC` 关卡；参数速查表补充 `L1_SEM_JAC | 0.75` 一行；把示例换成 3 条重复记录（唯一值 1/成员数 3 ≈ 0.33 < 0.5），使数字与结论一致。
