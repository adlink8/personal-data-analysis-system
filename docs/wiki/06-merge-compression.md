# 数据结构化与压缩

> **一句话：** 同一件事被记录多次（真重复）合并成 1 条，同一主题的不同记录（同主题）聚成 1 簇，原始数据一笔不动，只在叠加表里记合并关系。

---

## 为什么要合并

你的原始数据里存在两类冗余：

```
① 真重复：同一段对话被记录了两次，内容几乎一样
   → 浪费存储，检索时返回两条一样的

② 同主题：同一个话题（如"Python 调试"）反复出现
   → 检索时 10 条结果里 6 条关于 Python 调试，实际上 1 条就够了
```

合并层把这两类问题折叠掉，但不删原始数据。

---

## 三层策略

### L1：真重复检测（余弦 + 三重校验）

**判断标准：** 两条（或多条）事件内容几乎一模一样，仅 UUID/时间戳/路径不同。

**检测流程（实际是四关，代码里叫"三重校验"是指后三关的三重门槛）：**

```
余弦相似度 ≥ 0.97？                    → 第一关（向量级相似，先圈出候选连通分量）
  AND 原始文本 4-gram Jaccard ≥ 0.80？  → 第二关（字符级重合）
  AND 语义骨架 Jaccard ≥ 0.75？         → 第三关（去数字/路径/UUID 后的骨架重合）
  AND 语义骨架区分度 < 0.5？            → 第四关（防"结构相似"假阳性）
      │
  全部通过 → 确认为 L1 真重复 ✅
  任一不通 → 降级到 L2 重判
```

**第四关（内容区分度）是精髓：** 区分度 = 语义骨架去重后的唯一值数 / 簇内成员数，衡量"骨架相同但内容各异"的结构相似误判。

```
原始文本 A/B/C: "文档产物同步完成"（3 条几乎相同的记录，仅时间戳/UUID不同）

语义骨架（去数字/UUID后）:
  A/B/C → 骨架完全相同

唯一值=1，成员数=3 → 区分度 = 1/3 ≈ 0.33 < 0.5 → 通过 ✅（真重复）
```

如果文件名本身不同（如 `file_xxx.png` vs `file_yyy.png`），2 条记录的语义骨架唯一值=2，区分度 = 2/2 = 1.0 ≥ 0.5，第四关拦下，判定为"结构相似但内容不同"，降级到 L2。

**代表点选择：** 时间最早的那条。

### L2：同主题聚类

**判断标准：** 不同事件但说的是同一件事（如"Python 调试"相关）。

```
余弦相似度 0.88 ~ 0.97 的连通分量
  （含从 L1 降级下来的点）
      │
 排除已被 L1 处理的事件
      │
 簇大小 ≤ 50？ → 合并 ✅（生成摘要）
 簇大小 > 50？ → 结构保护，不解散不合并 → 交给 L3
```

**代表点选择：** 簇内平均相似度最高的（最居中的那条）。
**摘要生成：** 成员 title 去重（最多 5 个）+ 代表内容前 200 字。

### L3：不合并，保持原样

两类情况不进合并表：

```
① 超大簇（>50 条）→ 余弦虽高但数量太大，保护不解散
   例：几百条 SKILL.md 编辑记录 → 每条独立

② 独立事件（余弦 < 0.88）→ 跟谁都不相似，保持原样
```

## 合并层产出的表

```sql
merge_clusters（簇主表）
  cluster_id         'L1_8位hash' / 'L2_8位hash'
  level              'L1_duplicate' / 'L2_topic'
  representative_id  代表事件 ID
  member_count       簇大小
  summary            L2 摘要（L1 为空）
  mean_similarity    簇内平均相似度

merge_members（成员明细）
  cluster_id
  event_id
  is_representative  1=代表, 0=成员
  role               'rep' / 'duplicate' / 'topic_member'

merge_build_meta（构建元数据）
  key                'n_input', 'compression', 'threshold_l1_cos', ...
  value
```

**关键：** 原始 9 张统合表一字不改。任何时候 JOIN 回去都能拿到原始事件。

## 合并层在检索中的应用

语义搜索和精确查询都支持 `dedup=True`：

```powershell
rag-search "Python" --top-k 8 --dedup
rag-search query --source Agent --dedup --limit 30
```

内部逻辑：

```
_dedup_event_ids(event_ids)
  → 查 merge_members JOIN merge_clusters
  → 同一簇只保留代表
  → 每个结果附加 merged_count（折叠了多少条）
```

## 看一下实际压缩报告

```powershell
rag-search merge-stats
```

输出：

```
=== 合并层构建报告 ===
L1 真重复:        63 条 → 8 个代表     (省 55 条)
L2 同主题:     1,565 条 → 462 个簇    (省 1,103 条)
L3 结构保护:   3,492 条（5 个超大簇保持独立）
L3 保留原样:   2,486 条
────────────────────────
输入: 7,606 条 → 等效 6,448 条
净压缩率: 15.2%
```

### 这个数据说明了什么

| 指标 | 当前值 | 判断 |
|------|--------|------|
| L1 占比 | 63/7606 = 0.8% | ✅ **极低** — 上游归一化做得好，没有大量重复写入 |
| L2 占比 | 1565/7606 = 20.6% | ✅ **合理** — 同主题折叠在正常范围 |
| L3 结构保护 | 3492/7606 = 45.9% | ⚠️ **偏高** — 5 个超大簇占了一半数据，可能是系统日志/模板化事件 |
| 净压缩率 | 15.2% | ✅ **适中** — 不是越高越好 |

**压缩率不是越高越好。**

| 高压缩率可能的原因 | 实际问题 |
|-------------------|---------|
| L1 占比 > 20% | 上游写入有 bug，同一数据被重复写了几十次 |
| L2 阈值太松（如 0.80） | 把"Python 编程"和"JavaScript 编程"也合并了 |
| 禁用了超大簇保护 | 200 条 SKILL.md 强行合并成一个簇，代表无代表性 |

## 可调参数

| 参数 | 默认值 | 作用 | 调大 | 调小 |
|------|--------|------|------|------|
| `L1_COS` | 0.97 | L1 余弦门槛 | 更严，L1 减少 | 更松，L1 增加 |
| `L1_JAC` | 0.80 | L1 原始文本 4-gram Jaccard | 更严 | 更松 |
| `L1_SEM_JAC` | 0.75 | L1 语义骨架（去数字/路径/UUID）Jaccard | 更严 | 更松 |
| `L1_DISTINCT_RATIO` | 0.5 | L1 内容区分度 | 更易通过 | 更难通过 |
| `L2_COS_LO` | 0.88 | L2 余弦下界 | L2 减少 | L2 增加 |
| `L2_MAX_SIZE` | 50 | 超大簇保护阈值 | 更多大簇被合并 | 更多大簇被保护 |

代码位置：`application/graph/build_merge_layer.py`（阈值常量 + `detect_l1()` / `detect_l2()`）。
