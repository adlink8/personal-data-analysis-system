# 图数据库领域分类

> 配套文档:《SUMMARY_两个Demo反馈总结.md》第 6.3 节 FalkorDB 选型
> 日期:2026-06-17
> 目的:回答"都有什么数据库,每个是不是专门面向一定领域"

## 核心结论先说

**图数据库不全是"专门面向某领域"的，分两层看：**

1. **按数据模型分**（这是根本区别）：属性图 vs RDF 三元组 vs 多模型
2. **按优化场景分**（这是"领域"）：实时分析 vs 大规模分布式 vs 嵌入式轻量 vs 知识图谱推理

你的"图谱可视化"需求属于**属性图 + 实时分析**这一类，FalkorDB/Neo4j/Memgraph 都是这个定位。

---

## 一、按数据模型分类（根本区别）

### 1. 属性图数据库（Property Graph）—— 主流

**数据结构**：节点 + 边 + 属性（属性直接挂在节点/边上）

```
(用户:li)-[:使用 {频率:"高", 开始:"2026-01"}]->(工具:Codex)
```

**特点**：
- 查询语言多为 Cypher（Neo4j/FalkorDB/Memgraph）或类似语法
- 适合：关系网络、推荐、路径分析、你的记忆图谱
- **绝大多数图数据库都是这一类**

| 数据库 | 实现语言 | 查询语言 | 特点 |
|---|---|---|---|
| **Neo4j** | Java | Cypher | 鼻祖，生态最全，但 JVM 重 |
| **FalkorDB** | C（基于 Redis） | Cypher 子集 | **轻量首选**，Redis 底座 |
| **Memgraph** | C++ | Cypher | 内存优先，比 Neo4j 快 |
| **TigerGraph** | C++ | GSQL | 并行遍历，适合深度分析 |
| **NebulaGraph** | C++ | nGQL | 分布式，适合超大规模 |
| **HugeGraph** | Java | Gremlin | 百度开源，中文社区好 |
| **JanusGraph** | Java | Gremlin | 分布式，基于 Cassandra/HBase |

### 2. RDF 三元组数据库（Triple Store）—— 语义网/知识推理

**数据结构**：主-谓-宾三元组（Subject-Predicate-Object）

```
<用户li> <使用> <工具Codex>
<工具Codex> <属于> <编程工具>
```

**特点**：
- 查询语言是 SPARQL（比 Cypher 难学）
- 支持 OWL 推理（能推出隐含关系）
- 适合：学术知识图谱、医学/法律本体、语义搜索
- **不适合你的场景**（你不需要逻辑推理，只需要存储+查询）

| 数据库 | 特点 |
|---|---|
| **GraphDB (Ontotext)** | 商业，RDF 推理能力强 |
| **Apache Jena** | 开源，学术常用 |
| **Stardog** | 商业，支持 OWL 推理 |
| **Virtuoso** | 开源，DBpedia/Wikipedia 底层 |

### 3. 多模型数据库（Multi-Model）—— 一库多用

**特点**：一个数据库同时支持 文档 + 图 + 键值 + 关系，用不同 API 查。

| 数据库 | 支持的模型 | 适合 |
|---|---|---|
| **ArangoDB** | 文档 + 图 + 键值 | 想一个库搞定多种数据 |
| **ArcadeDB** | 文档 + 图 + 时序 | 多模型，2026 新秀 |
| **OrientDB** | 文档 + 图（已停更） | 历史项目 |

## 二、按优化场景分类（这才是"领域"）

### 场景 1：实时分析 / 交互式查询（你的场景）

**特征**：数据量中等（万~百万节点），需要毫秒级响应 + 图谱可视化。

| 首选 | 理由 |
|---|---|
| **FalkorDB** | Redis 底座，内存占用小，自带 Web UI，部署最轻 |
| **Memgraph** | C++ 内存优先，Cypher 兼容，自带 Lab 可视化 |
| Neo4j | 生态最全，但 JVM 重 |

### 场景 2：超大规模分布式（十亿+节点）

**特征**：单机放不下，需要分片。

| 数据库 | 特点 |
|---|---|
| **NebulaGraph** | 国产，支持千亿节点 |
| **JanusGraph** | 基于 Cassandra/HBase，可扩展 |
| **AWS Neptune** | 云托管，省运维但锁定 AWS |
| **HugeGraph** | 百度开源，分布式 |

### 场景 3：深度图算法 / 机器学习

**特征**：需要 PageRank、社区检测、图神经网络（GNN）。

| 数据库 | 特点 |
|---|---|
| **TigerGraph** | 内置并行遍历引擎，算法库全 |
| **Dgraph** | Go 写的，支持图 + 向量（适合 RAG） |
| **PuppyGraph** | 2026 新秀，主打图 + 向量融合 |

### 场景 4：嵌入式 / 轻量（你的备选方案）

**特征**：不需要独立服务，嵌在应用进程里。

| 方案 | 特点 |
|---|---|
| **SQLite + networkx** | **你现在的方案**，零外部依赖 |
| **DuckDB + 图扩展** | 嵌入式分析数据库，支持图查询 |
| **pyvis + networkx** | 纯 Python 图谱可视化，生成 HTML |

### 场景 5：语义推理 / 知识图谱

**特征**：需要从已有关系推出新关系（如"A 是 B 的父亲"+"B 是 C 的父亲"→"A 是 C 的祖父"）。

| 数据库 | 特点 |
|---|---|
| GraphDB (Ontotext) | 商业，RDF + OWL 推理 |
| Apache Jena | 开源，学术研究 |
| Stardog | 商业，企业知识图谱 |

## 三、可视化能力对比（你关心的点）

| 数据库 | 自带可视化 | 第三方可视化 |
|---|---|---|
| **Neo4j** | ✅ Browser(7474)，最成熟 | Bloom, Gephi, yEd |
| **FalkorDB** | ✅ Web UI(3000)，类 Neo4j | RedisInsight |
| **Memgraph** | ✅ Lab，现代界面 | Graphileon |
| TigerGraph | ✅ GraphStudio | - |
| ArangoDB | ⚠️ 基础 Web UI | C8Studio |
| RDF 类 | ❌ 需第三方 | Gephi, Neo4j(导入) |

**可视化体验最好的前三**：Neo4j Browser > FalkorDB Web UI > Memgraph Lab。

## 四、针对你的项目的选型矩阵

| 你的需求 | 推荐方案 | 理由 |
|---|---|---|
| 当前 194 条记忆 | **SQLite + networkx + pyvis** | 零外部依赖，已有数据结构 |
| 想体验图数据库 | **FalkorDB** | 比 Neo4j 轻 10 倍，一行 Docker |
| 数据涨到 5000+ 且需多跳 | **Memgraph 或 FalkorDB** | 内存优先，Cypher 兼容 |
| 需要分布式 | NebulaGraph | 国产，中文文档好 |
| 需要语义推理 | GraphDB / Jena | RDF + OWL |
| 想要图 + 向量融合 | Dgraph / PuppyGraph | 适合 RAG 增强 |

## 五、常见误区澄清

**误区 1："图数据库就是 Neo4j"**
错。Neo4j 只是属性图里最知名的一个。FalkorDB/Memgraph 在很多场景下更合适。

**误区 2："图数据库专门面向社交网络"**
部分对。社交网络是典型用例，但你的记忆图谱、知识管理、推荐系统、欺诈检测、IT 架构图都是图数据库的领域。

**误区 3："RDF 数据库和属性图数据库功能一样"**
错。RDF 能做**逻辑推理**（推出隐含关系），属性图不能。但属性图**查询更直观**、可视化更好。

**误区 4："必须用图数据库才能做图谱"**
错。你的 SQLite + networkx 就是图谱，只是没有专门的图查询引擎。在 200 条规模下完全够用。

## 六、本次选型结论

**FalkorDB 作为本项目的"未来候选图数据库"**，理由：
1. 基于 Redis，内存占用是 Neo4j 的 1/4
2. Cypher 语法兼容，迁移成本低
3. 自带 Web UI 可视化
4. SSPL 协议，源码开放
5. Graphiti 官方支持，无需改 Graphiti 代码

**但当前不引入**，判定阈值：
- `memory_items` > 5000 条
- 或需要频繁多跳查询 + 交互式拖拽下钻
