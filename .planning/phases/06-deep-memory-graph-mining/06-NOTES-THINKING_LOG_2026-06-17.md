## 一、三层存储架构的理解

从"向量数据库搭配图数据库搭配关系数据库"出发，确立了三层职责：

```
关系数据库（SQLite）→ 保原文、保可靠性、保溯源
向量数据库（Qdrant）→ 找语义相近内容
图数据库（FalkorDB）→ 找多跳关系、补足 SQL JOIN 的不足
```

三层不是冗余，是分工。项目已有前两层，图数据库是下一步。

---

## 二、余弦相似度

- 核心：不比距离，比方向
- 文字 → embedding → 向量 → 算夹角余弦值
- 值越接近 1 语义越相似
- 优于欧氏距离的原因：不受文本长短影响，只看语义方向

---

## 三、三层架构对基础 RAG 的提升

基础 RAG 缺陷：块割裂、无关系感知、无溯源、无时序

三层补的缺口：
- 向量召回候选
- 图扩展上下文
- 关系库防幻觉兜底

业界现状对照：

| 项目 | 核心思路 | 与本项目的关系 |
|---|---|---|
| GraphRAG（微软） | 图社区检测 + 层级摘要 | 本项目缺社区摘要层 |
| LightRAG | 图 + 双模式检索 | GraphRAG 轻量替代 |
| RAPTOR | 递归摘要树 | 长文档全局理解 |
| CRAG | 检索后质量评分 | 本项目缺召回评分 |
| Agentic RAG | Agent 迭代检索 | 复杂推理链 |

本项目对标基准线已达到，差距在：社区摘要、检索质量评分。

## 四、个人成长操作系统的完整愿景

核心：23 岁起用 10 年构建只属于自己的个人生命操作系统

```
数据来源：对话 / Obsidian / GitHub / 健康 / 财务 / 决策
处理层：  统一事件 → 记忆提炼 → 向量 + 图检索
分析层：  个人画像 → 反馈闭环 → 个人算法
目标：    系统越用越懂你，最终参与你的决策
```

核心护城河：数据主权在本地，长期可迁移，别的产品换一次断一次，自己的数据一直是自己的。

**系统能否追风口和指导成长：**

- 能做到：基于真实历史给专属建议，比通用 AI 建议更贴合
- 做不到：替代执行速度，也补不了外部信息差
- 追风口正确姿势：接入外部信号源（arxiv / GitHub trending / 招聘数据）→ 和技能图谱做匹配 → 输出专属入场成本判断

本项目本身就是下一个垂直风口的原型：个人数据主权工具 × AI 记忆系统。

## 五、两个项目的关系厘清

**Obsidian Vault** = 和 AI 对话后，主动整理提炼的思考层（人写人读）

**数据分析项目** = 所有个人数据的全量大杂烩（机器处理）

关键发现：Obsidian README 里写"计划中"的东西（SQLite 层、向量检索、pipeline），数据分析项目已经建好了。两个项目是同一愿景的两半，不是竞争关系。

```
Obsidian 的笔记 = 已经被人工验证过的高质量信号
  → 导入后打 source=obsidian 高权重
  → 经过人工提炼一次，质量高于 pipeline 自动提炼

Agent/GPT 对话 = 思考嵌在原始对话里，未提取
  → pipeline 自动提炼

Google/GitHub = 行为数据，不一定是深度思考
  → 权重最低，参考用
```

## 六、Mem0 的正确接入位置

**原始误判：** Agent/GPT 流不该用 Mem0，因为原文会消失

**纠正：** Mem0 不删原文，只是高质量压缩，原文依然保留在 unified_events

**最终架构：两级提炼**

```
unified_events（原文永久保留，唯一真相源）
    │
    ├──────────────────────────┐
    ▼                          ▼
Mem0 预压缩（第一级）      原文兜底
高质量结构化压缩           （Mem0 漏掉的 ~15%）
    │                          │
    └──────────┬───────────────┘
               ▼ 合并去重
          pipeline 精炼（第二级）
          ├── 自定义过滤
          ├── 分类（能力/偏好/上下文）
          ├── 打 evidence_ids（链回原始事件）
          └── 写入 memory_items
```

两级优于单用任何一个：
- Mem0 让 pipeline 输入更干净，提炼质量上限更高
- pipeline 保留自定义逻辑和溯源链，Mem0 补不了这个
- 原文兜底保证 Mem0 的 15% 噪音不造成永久丢失

## 七、最终架构决策

**Obsidian 停止维护，历史数据一次性导入数据分析项目。**

理由：
- 维护两套系统成本高，职责边界模糊
- Obsidian 思考内容通过 obsidian_adapter 导入后，evidence_ids 仍指向原始 md 文件，不丢失
- 导入时打 `source=obsidian` 高权重标记

**最终一条流：**

```
所有数据来源
（对话 / Google / GitHub / Obsidian历史 / 未来健康财务）
    ↓
unified_events（唯一真相源，原文永久保留）
    ↓
Mem0 预压缩（第一级）+ 原文兜底
    ↓
pipeline 精炼（第二级）
    ↓
memory_items + evidence_ids
    ↓
向量库（Qdrant）+ 图数据库（FalkorDB，未来）
    ↓
个人成长操作系统
```
