# Plan 21-03: Knowledge Domain Migration

## Goal

Third batch. Relocate the 16 knowledge build/orchestration scripts to `application/knowledge/` and the 3 evaluate scripts to `evaluation/knowledge/`, leaving re-export facades (D-06/D-07). The schema-constant module `migrate_add_knowledge_unit_tables.py` (which only defines the `SCHEMA_SQL` DDL constant used by tests as a fixture) STAYS in `domains/knowledge/` — it is a pure domain constant per the CONTEXT success criterion "domains 只剩纯 domain 规则/模型/常量". Build scripts first, then eval (D-04). Depends on 21-01 (peer-import pattern is now established).

## Context references

- Facade template: `src/personal_knowledge/retrieval/unified_search.py` L18-58
- Layer rule: `governance/policies/architecture.yaml` L18 (`knowledge: layer: domain`), L22 (`pipeline`=application may_import includes knowledge), L24 (`evaluation` may_import includes knowledge), L29 (`knowledge forbidden→pipeline/services/evaluation` — the facades introduce a documented, time-boxed exception identical to phase-1)
- `promote_knowledge_index.py:219` imports `personal_knowledge.evaluation.gate_knowledge_candidate` — this knowledge→evaluation import is a CURRENT violation in the domain layer; once `promote_knowledge_index` moves to `application/knowledge/`, the import becomes LEGAL (pipeline may_import includes evaluation). This is the "顺带修正" noted in CONTEXT.
- Path-bootstrap risk: `refresh_knowledge_units.py:24`, `knowledge_unit_pipeline.py:36`, `build_knowledge_units_prod.py:46` each compute `_SCRIPTS_DIR = Path(__file__).resolve().parents[1]` and `sys.path.insert` it. After moving to `application/knowledge/`, `parents[1]` resolves to `application/` instead of `domains/`. Investigation shows `_SCRIPTS_DIR` is ONLY used for the `sys.path` bootstrap and as `_THIS_DIR` legacy alias — no sibling-script file lookup. Verify post-move that no bare-name import depends on the old path (see Task 4 audit).
